# Cofinite integral braces on low dimensional crystallographic groups

This repository contains the code needed for determining isomorphim classes of *cofinite integral braces* up to dimension 6.

The code uses the following tools:

- [GAP](https://gap-system.org) - this is the base: almost all the code is written for GAP
- [CARAT](https://github.com/lbfm-rwth/carat) - as a standalone database and toolbox for crystallographic groups up to dimension 6
- [REDIS](https://redis.io) - in memory database, used in distributed computations
- [GNU Parallel](https://doi.org/10.5281/zenodo.17692695)

In addition, two GAP packages were developed to reach the goal:

- [CIB](https://github.com/rlutowsk/cib) - a package for calculation with cofinite integral braces in GAP
- [REDIS](https://github.com/rlutowsk/redis) - a GAP interface to Redis database

# Reproducing the results

## Generate crystallographic groups

This may be seen as a common task when one works with CARAT. It is a process of generating all crystallographic groups with point (holonomy) groups forming one conjugacy class of GL(n,Q). For example, let's work with conjugacy class with the representative called `group.1044` in CARAT, for which n=6.

1. Determine the representatives of conjugacy classes in GL(6,Z) (or Z-classes) of those groups which are all conjugated over Q:

    ```bash
    QtoZ -D group.1044
    ```

    As an output we get two files: `group.1044.1.1` and `group.1044.1.2`.

1. For every representative of the Z-class, determine all crystallographic groups:

    ```bash
    for x in group.1044.*; do Extensions -S pres.group.1044 $x; done
    ```

> [!TIP]
> Database of CARAT stores presentation of groups. It is advisable to use those files in order to avoid some current bugs.

> [!NOTE]
> Data generated by CARAT is located in `data/` subfolder. The code is ready to handle this prepared files.

## Migrating data to Redis database

> [!IMPORTANT]
> Redis instance must be up. GAP package `redis` must be compiled and loaded. One can always check the connection, ori simply connect to the server:
> ```gap
> gap> LoadPackage("redis");
> gap> RedisConnect("localhost", 6379); # connect to the same machine on the default port
> ```

> [!NOTE]
> In the example we will use the right acting crystallographic groups. This is how the GAP package `CIB` is designed, which is in a way default behaviour of group actions in GAP.

1. Initiate data structures, point to the data folder (`data/`) in our case:

    ```gap
    gap> CaratCatInit("data");
    ```
1. Load the dataset into GAP (into `CDB` record):

    ```gap
    gap> CaratCatReadEncodedRight();
    ```
1. Save the dataset in Redis:

    ```gap
    gap> CaratCatSaveZClasses();
    gap> CaratCatSaveCocycles();
    gap> CaratCatSaveQClasses();
    gap> CaratCatSaveTorsionfree();
    ```

## Running the calculations

1. Prepare the list of Z-classes. Since the algorithms sometimes depened on calculations in subgroups, we will sort it by the group order.

    ```gap
    gap> dim := 6;;
    gap> znames := RedisCommand("SMEMBERS zclasses:dim:{}", dim);;
    gap> zclasses := List( znames, CaratCatFetchZClass );;
    gap> SortBy( zclasses, x->x.size );
    ```
1. Prepare the queue - a Redis list `ainput`:

    ```gap
    gap> for z in zclasses do
    >   for a in RedisCommand("SMEMBERS {}:anames", z.name) do
    >       RedisCommand("LPUSH ainput {}.{}", z.name, a);
    >   od;
    > od;
1. One must modify the `run.g` script to run one of the worker functions:

    - `CIBRunJob`: checks the crystallographic groups for CIB structures by enumerating all possible cocycles. Good for smaller point groups.
    - `CIBRunJob1`: Uses database information about subgroups of a given crystallographic groups. The overhead of this checking may be unnecessary large for groups with small point group. Better for groups of order greater than 32.
    - `CIBRunJobCheck`: this is only for recalculation and checking if the database information is consistent.

> [!IMPORTANT]
> All the above functions are designed to work in distributed environment. Hence the arguments are as follows:
>
> - `queue`: Redis list containing the CARAT names of crystallographic groups. This is the input queue.
> - `set`: Redis set containing groups which are currently being calculated. In the case of a crash of a worker process, the name remains and can be moved to the input queue.
> - `key`: this is for the generating functions - the name of the Redis hash key which stores the calculated vector systems (cocycle data) for CIB structure on given crystallographic group.

# Reading the data

The data were exported to files in JSON format. For every Z-class we have the following fields:

- `dim`: the dimension of the group
- `name`: the name of the Z-class of the group
- `size`: the order of the group
- `generators`: matrices generating the group
- `normalizer`: matrices generating the normalizer of the group in GL(dim,Z)
- `aff`: list of records correspoding to the affine classes (crystallographic groups) in the given Z-class, with the following entries:

    - `no`: number of the extension in CARAT catalogue
    - `vs`: vector system; the images of the cocycle under the generators to be precise
    - `cib`: list of vector systems (as in `vs`) that correspond to representatives of isomorphism classes of cofinite integral braces with given crystallographic multiplicative group
